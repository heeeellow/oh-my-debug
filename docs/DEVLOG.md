## 2026-08-28：工作台演进启动

### 目标

在不回归现有双端点串口能力的前提下，将单窗口 DEMO 演进为设备中心的调试工作台，并为板端
Agent 留出稳定边界。

### 基线事实

- Qt 界面、设备扫描、连接管理和串口测试集中在一个约 42 KB 的 `test.cpp` 中。
- 串口传输已经通过不依赖 Qt 的 `ISerialTransport` 抽象。
- Windows 串口使用 CSerialPort；板端串口使用 `adb forward ... dev:/dev/...`。
- 当前发布目录只有主程序，没有独立部署依赖集合。
- 当前工作区不是 Git 仓库，无法使用提交作为回退入口；修改前后必须依赖文件差异和构建产物核对。

### 设计决策

- 开发记录改为仓库内的架构、UI、开发手册和里程碑日志，不使用故障 Review 作为主体结构。
- 第一阶段实现固定布局的工作台外壳并拆分串口页面。
- 参考 Qlementine、Fluent-Qt 和 Qt Creator，但暂不引入第三方 UI 依赖。
- 板端 Agent 使用版本化、长度前缀协议；详细约束见 `ARCHITECTURE.md`。

### 当前验证

- 架构：已完成编码前自审，允许进入第一阶段实现。
- 分层：`core/` 与 `application/` 的 Qt 类型/头文件扫描无命中。
- 构建：Visual Studio 18 + Qt 6.11.2，`x64 Release` 全量重建通过。
- 核心自测：通过编码检查、ADB 在线设备枚举、3 个板端串口枚举及安全 `dev:/dev/null`
  转发创建/清理。
- UI 快照：概览页和串口工作台在 1440×900 逻辑窗口下通过人工视觉检查；未出现裁切、重叠
  或错误的操作层级。
- 实机串口：本轮没有在未知接线条件下打开 COM1 与 `/dev/ttyS2`，因此真实收发和双向回环仍是
  明确未覆盖项。

## 2026-08-28：串口可用性与退出稳定性

### 现场问题与结论

- RK3562 设备以 `shell` 身份运行 adbd 时无法读写 `root:root 0600` 的 `/dev/ttyS6`；这不是
  Windows 串口库错误，而是板端设备节点权限与 adbd 身份不匹配。
- 原发送流程在 HEX 分支提前返回，导致所选行尾没有附加；双向验证帧也没有使用端点行尾设置。
- 监视区只记录 RX，发送 AT 指令时无法从同一时间线确认实际发送内容。
- UI 快照退出崩溃可稳定复现，原因是 ADB 扫描线程可能在 Qt 对象销毁期间继续投递回调。

### 本轮处理

- ADB 直连先探测节点是否存在以及是否可读写；权限不足时可显式尝试 `adb root`，等待设备重新
  上线后复查。量产版不支持 root 或 SELinux 仍阻止访问时，错误会引导使用板端 Agent。
- 文本与 HEX 发送统一在纯 C++ 编码层附加 `LF`、`CR` 或 `CRLF`；双向验证沿用各端点设置。
- 收发监视区增加 `TX`/`RX` 方向标记，文本模式将不可见的回车换行显示为 `\\r`、`\\n`。
- 应用退出时先停止新任务、断开传输、等待扫描线程，再销毁 Qt 对象；后台回调增加关闭状态检查。
- 建立 Git 基线提交，第三方源码以 vendored 方式记录来源和本地适配，后续演进可按里程碑回退。

### 验证

- `x64 Release` 构建通过，0 个警告、0 个错误。
- 核心自测覆盖 HEX 编解码和 `AT + CRLF` 字节结果，并通过 ADB 设备/端口/安全转发检查。
- 1440×900 串口页连续执行 20 次启动、扫描、截图和退出，20/20 正常，未再出现
  `0xC0000005`。
- 实机确认 RK3562 的 shell 权限探测失败，`adb root` 后身份切换为 `uid=0` 且端点可访问；验证后
  已执行 `adb unroot` 恢复 `uid=2000(shell)`。真实串口收发仍需在确认接线和端口用途后验收。

## 2026-08-28：自动发送、可靠性压测与 Agent v1 雏形

### 串口测试能力

- 每个端点增加按需配置的自动发送：10–60000 ms 间隔、有限次数或持续发送，并默认将 TX 记录
  到收发监视。配置放入弹窗，避免压缩长期使用的监视区。
- 增加链路可靠性压测，可选择 A→B、B→A 或双向，配置每方向帧数、载荷长度和发送间隔。
- 测试帧包含同步标记、版本、长度、序号、确定性载荷和 CRC32；流式校验器处理拆包、粘包、
  噪声重同步、重复帧、坏帧和载荷位差异。
- BER 只以已解析帧中可比较的有效载荷位为分母；丢帧与格式错误单独报告，避免给出含义不清的
  “综合误码率”。
- 可靠性帧要求两端使用 8 数据位；当用户间隔低于按波特率和帧格式估算的线速时长时，界面明确
  提示并使用可实现的间隔，避免测试数据在主机队列中虚假堆积。
- 串口写入移至纯 C++ 有界后台队列，GUI 线程不再因低波特率、大帧或连续发送直接阻塞。

### Agent 雏形

- 增加无 Qt 的 `testtools-agent.exe` 假服务，只绑定 `127.0.0.1`。
- 增加最大 1 MiB 的长度前缀帧编解码和无 Qt 的 `AgentClient`。
- 假服务实现 `session.hello`、`capability.list`，只声明只读 `system.info`，不执行任意 shell。
- 本机 TCP 冒烟验证 hello 与能力发现通过；当前客户端仍为同步测试客户端，尚未接入 GUI 会话。

## 2026-08-28：Android 串口兼容与 Agent 主界面接入

### Android 串口现场结论

- RK3562 当前 `/dev/ttyUSB0/1/2` 为 `radio:radio 0660`，`/dev/ttyS6` 为 `root:root 0600`；
  adbd root 后权限检查均通过，SELinux 为 Permissive。
- `/dev/ttyUSB0` 和 `/dev/ttyUSB2` 只拒绝设置 `115200`，其余 raw、数据位、校验、停止位和流控
  设置通过；ADB `dev:` 转发与本地 TCP 连接均正常。USB modem 驱动的物理链路不是传统 UART
  时钟，拒绝 termios 波特率不应被视为打开失败。
- `/dev/ttyUSB1` 被 `rild`（PID 388）占用。直接并行打开会干扰 4G 系统服务，因此保持阻止并
  明确报告占用者，不以强制抢占作为修复。
- RK3562 上不存在 `/dev/ttyS2`；Nexus 4 上的 `/dev/ttyS2` 以及 RK3562 的 `/dev/ttyS6` 均完成
  termios、ADB 转发和 TCP 连接冒烟，未发送任何数据。

### 修正

- USB/ACM 串口完整 `stty` 失败时，自动重试不包含波特率的全部帧格式设置；只有第二次也失败
  才终止连接。
- 打开前在系统提供 `lsof` 时检查占用进程，为 `rild` 等系统服务给出明确且安全的错误。
- 传输状态从 `bool + 文本前缀推断` 改为 `Progress/Connected/Error/Closed` 枚举，避免提示信息
  被误判为失败。

### Agent 主界面

- 设置页增加“一键启动并连接假 Agent”和本机/ADB 转发端口连接入口。
- Agent 握手和能力发现在线程中执行，socket 收发超时为 5 秒，不阻塞 GUI。
- 顶栏、概览和设置页同步显示版本、连接状态与 `system.info（只读）` 能力。
- 连接地址暂时只允许 `127.0.0.1`，假 Agent 退出或应用关闭时会关闭会话并清理子进程。
- 当前 RK3562 为 Android 13、`armeabi-v7a`；开发机未发现可用 Android NDK，因此本轮交付的是
  Windows 假 Agent 与完整连接界面，板端 Agent 的交叉编译、推送和守护启动留作下一阶段。
- 主程序工程显式依赖假 Agent 工程，两者统一输出到同一运行目录，避免单独命令行构建后界面
  误用旧版 Agent 或提示缺少程序。

## 2026-08-29：真实 Android Agent 与托管串口流

### 现场诊断

- 当前只连接 RK3562 Android 13 设备 `e2ea0f728463744a`，ABI 为 `armeabi-v7a`，adbd 身份为 root。
- `/dev/ttyUSB2` 是 Quectel EG800AK-CN 的 `Mobile AT Interface`，未被进程占用；
  `/dev/ttyUSB1` 同为 AT 接口，但由 `rild`（PID 388）占用。
- 旧 `adb forward dev:/dev/ttyUSB2` 虽能返回本地端口，但连接会立即 EOF；`ttyUSB0` 与 `ttyS6`
  表现相同，目标 adbd 又不支持 `dev-raw:`。因此问题不是 chmod 或波特率设置，产品路径改为 Agent
  托管串口。

### 实现

- Agent `0.2.0` 增加真实 `system.info`、`serial.list`、`serial.open` 和 `serial.close`，使用 POSIX
  termios、文件锁和回环 TCP 原始数据通道，不依赖 Qt。
- 设置页移除假 Agent 和手工主机/端口输入，改为选择设备后“一键部署 / 更新并连接”。部署过程自动
  识别 ABI、推送到 `/data/local/tmp/testtools-agent/`、记录 PID、启动、探测日志并创建控制转发。
- 串口工作台移除用户可见的 ADB 直连与 root 开关，板端串口经真实 Agent 枚举和打开；占用进程直接
  显示在端点名称旁。当前 Agent 为单板端串口会话，界面阻止两路 Agent 串口同时打开。
- 普通计划发送改名为“定时 / 次数发送”，仍使用用户输入的内容和行尾；可靠性压测继续使用带序号与
  校验的数据帧，两者保持独立入口和状态。
- 增加 `scripts/build-android-agent.ps1`，Android Agent 构建产物按 ABI 复制到主程序运行目录。

### 验证

- Android NDK r27d、API 23、静态 libc++ 构建成功，产物为 ARM 32-bit ELF。
- Windows Release 主程序零警告、零错误构建通过。
- `--agent-deploy-smoke` 在实机完成 ABI 识别、替换部署、启动、`system.info` 和 `serial.list`，结果
  PASS；首次验证发现 toybox 不支持 `setsid -f` 且旧 Agent 无法退出，已改为 nohup、PID 文件和
  兼容旧版本的进程清理后复测通过。
- `--agent-serial-smoke e2ea0f728463744a <control-port> /dev/ttyUSB2` 打开数据通道并空闲保持 5 秒，
  结果 PASS，测试明确未发送任何串口字节。
- 设置页和串口页在 1360×860 完成快照检查，无裁切和重叠。

### 当前边界

- 尚未向 4G 模块发送 AT 指令；真实命令收发留给用户在已知安全场景下验收。
- 下一阶段应先实现 Agent 多会话资源表和心跳/断线恢复，再扩展并发测试项与任务历史。

### Debug 运行目录与 ttyUSB2 速率复查

- 用户从 Visual Studio 运行的是 `test/x64/Debug/test.exe`，而先前 Android Agent 只生成在 Release
  目录；Debug 运行时找不到本地部署产物，这是“无法发现并连接 Agent”的直接原因。
- 主工程现在在发现 NDK 时自动构建 Agent，并复制到当前 Debug/Release 运行目录。Debug 实测生成
  `agents/android/armeabi-v7a/testtools-agent`，部署、串口保持和现有 Agent 重连均为 PASS。
- 连接流程先探测 PID 文件与板端现有进程并尝试握手；只有未运行或握手失败时才重新部署，避免把
  “发现”错误地等同于每次覆盖安装。
- 界面启动或切换 ADB 设备后会安全探测现有 Agent；串口页发现多个板端节点时，优先选中未占用且
  可读写的 AT 接口。本板实测默认落在 `/dev/ttyUSB2 — Mobile AT Interface`，并避开 `rild`
  占用的 `/dev/ttyUSB1`。
- `/dev/ttyUSB2` 确认为 `option1` USB 串口驱动的 `Mobile AT Interface`。Agent 请求 115200 后，
  Agent 文件描述符和板端 `stty` 均报告 9600；这说明 115200 没有作为可验证的物理速率生效。
  对该 USB AT 接口，通信走 USB bulk，波特率为兼容参数而非 USB 链路速率。界面状态现会同时显示
  请求值和内核报告值，避免误导。

### ttyUSB2 AT 实机复查与目录整理

- 通过与产品一致的 Agent 控制帧和原始数据通道直连 `/dev/ttyUSB2`：发送 `41 54 0D 0A`
  （`AT\r\n`）收到 `0D 0A 4F 4B 0D 0A`（`OK`）；发送 `ATI\r` 收到 Quectel
  `EG800AK`、固件版本与 `OK`。由此排除 ttyUSB2 权限、Agent 转发和接收线程故障。
- 新增 `--agent-at-smoke` 后再经界面实际使用的 `AgentSerialTransport` 完整链路复测，发送
  `AT\r\n` 同样收到 `OK`，自检、现有 Agent 重连和 AT 冒烟退出码均为 0。
- 源码从含义不清的 `test/` 收拢到 `src/{application,core,agent,diagnostics,ui}`，第三方依赖提升到
  根目录 `third_party/`，解决方案统一命名为 `TestTools.slnx` / `TestTools.vcxproj`，全部生成物统一
  输出到未跟踪的 `build/`。同时删除未参与构建的空白 `test.ui` 与 `test.qrc`。
- 首次整理时主解决方案同时包含 Qt GUI 和 Windows Agent 控制台工程，Visual Studio 可能把后者
  选为启动项目，表现为编译后只出现终端。主解决方案现只保留 `TestTools.vcxproj`；Windows Agent
  工程仍可独立构建，Android Agent 继续由 GUI 工程的构建目标自动生成。
