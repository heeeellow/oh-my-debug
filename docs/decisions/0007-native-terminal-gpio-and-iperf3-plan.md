## 1. 背景与痛点分析

以下是 P0 前 `0.14.2` 基线的使用反馈与代码体检，不能作为整理后的当前状态。该基线工作台在架构可维护性与高频调试场景下存在四个突出问题：

1. **串口终端与单/双串口工作区强耦合，且仓库存在历史残留**：
   - 主窗口的“串口终端”页面目前通过 [`MainWindow::buildSerialPage(true)`](../../src/ui/main_window.cpp) 创建**第二个 [`SerialWorkspace`](../../src/ui/pages/serial_workspace.cpp) 实例**（单文件已达 3351 行），在内部隐藏通道 A、发送框与快捷指令侧栏，仅借用 `channels_[1]` 运行终端。这导致终端实例在后台冗余创建了双通道控件、双向验证、压测状态机与常驻 10ms 定时器，且无法自然演进为“串口 + 内嵌 ADB Shell”多标签结构。
   - 仓库内留有早期未接入产品的死代码（如 `board_profile.*`）、废弃的 `TestToolsAgent.vcxproj`，以及超过 4.27 GB 的旧版迭代构建缓存与散落 `.obj` 文件。
2. **终端体验未能达到日常主力终端（Windows Terminal / Tabby）的流畅度与手感**：
   - **刷屏卡顿**：现有 [`ReceiveConsole`](../../src/ui/widgets/serial_receive_view.h) 基于 `QPlainTextEdit`，[`SerialWorkspace::renderTerminal`](../../src/ui/pages/serial_workspace.cpp) 每次刷新通过 `QTextCursor` 修改 `QTextDocument` 富文本块并重建 `ExtraSelections`。在内核启动日志、`dmesg` 或高波特率连续输出下，GUI 线程频繁承担文档排版与高亮重算，导致界面卡顿。
   - **复制粘贴不顺手**：现有契约将 `Ctrl+C` 固定为发送 `0x03`，复制必须按 `Ctrl+Shift+C`，且缺少双击选词、三击选行、矩形块选、选中即复制/右键粘贴、自动折行长行还原与多行粘贴安全确认。
   - **显示效果欠佳**：`QTextDocument` 的行高、字距、CJK 双宽字符对齐、Box Drawing 制表框线及反色光标并非严格字符网格，且缺少备用屏幕（Alternate Screen Buffer），无法正常操作 `vim`、`top`、`htop`、`menuconfig`。此外，ADB Shell 仍需弹出外部系统终端窗口，与串口终端割裂。
3. **缺少板端硬件引脚（GPIO）的快速观测与控制入口**：
   - 硬件联调常需拉高/拉低使能脚（如外设电源、复位脚、LED）或观测按键/中断输入电平变化；目前需切到外部终端手敲 `/sys/class/gpio` 或 `gpioset` 命令，操作繁琐且易误触内核已占用引脚。
4. **缺少一键以太网吞吐测速（iperf3）**：
   - 板卡以太网验收常需测试 PC ↔ 板卡的上下行吞吐，手动在两端起停 `iperf3`、核对网卡 IP 与协商速率耗时较长，且需要所有二进制随程序打包、开箱即用。

## 3. 终端模式重塑方案（分 T1 / T2 两步推进）

### 3.1 技术选型：`libvterm` + 字符网格自绘控件（`TerminalGridWidget`）

| 候选方案 | 架构与体验评估 | 结论 |
| --- | --- | --- |
| **`libvterm`（纯 C，MIT）+ Qt 字符网格自绘** | 标准 C 实现完整 VT220/xterm 状态机、主/备屏幕、滚动区（scroll region）、宽字符与鼠标报告；不依赖 Qt，可直接放入 `src/application/serial/`，完全符合无 Qt 分层边界；UI 层继承 `QAbstractScrollArea` 按可见行列与脏区（damage）绘制，吞吐高、内存可控 | **采用** |
| `xterm.js` + WebView2 / Qt WebEngine | 视觉接近 Tabby，但引入浏览器运行时与跨进程 JS 桥接，包体积、内存占用和离线分发复杂度显著增加 | 不采用 |
| `QTermWidget` | GPL 许可证且强耦合 POSIX/Linux 伪终端，Windows 适配薄弱 | 不采用 |
| 继续修补现有 `SerialTerminalBuffer` + `QPlainTextEdit` | 无法从根本上消除 `QTextDocument` 重排开销，补齐备用屏幕和复杂 CSI 的维护成本高于引入成熟库 | 不采用 |

### 3.2 T1：串口终端引擎替换与原生交互手感

#### 1. 渲染与高吞吐防卡顿架构
- **后台解析与双缓冲快照**：串口接收字节先进入录制队列（保持录制独立性），随后在后台终端工作线程喂入 `libvterm` 并更新屏幕网格与回滚环形缓冲（默认 20000 行上限）；GUI 线程不执行 VT 解析。
- **帧率解耦（Frame Coalescing）**：后台产生脏行（damage）时只置位原子通知标志；GUI 按固定帧预算（约 16ms / 60Hz）拉取最新可见视口快照并仅调用 `viewport()->update(dirtyRect)`。当串口以 1.5 Mbps 连续刷屏时，自动跳过中间帧、直接渲染最新一屏，以主机回放记录 GUI 响应、绘制耗时与内存，不能承诺所有环境下零卡顿。
- **严格字符网格渲染**：
  - 预计算等宽字体（`Cascadia Mono` / `Consolas`）固定单元格尺寸 `cellWidth × cellHeight`，ASCII 占 1 列、CJK 宽字符占 2 列。
  - `U+2500..U+257F` 制表框线（Box Drawing）与块元素采用 `QPainter` 几何自绘，确保 `menuconfig`/`htop` 边框严丝合缝、不随字体行距断裂。
  - 完整支持 16 标准色、256 色、24-bit TrueColor、粗体、斜体、下划线、反色，以及块状（Block）、竖线（Bar）、下划线（Underline）光标和窗口失焦空心框光标。
  - 默认提供原生感深色终端配色（如 One Dark / Campbell 柔化版），同时在“终端外观”中提供暖白浅色与高对比配色、字号（11–18px）及行高微调，偏好持久化至 `terminal-preferences.json`。

#### 2. 复制粘贴与键盘交互（对齐 Windows Terminal / Tabby）
- **智能 `Ctrl+C` / `Ctrl+V`（默认开启，可切回传统模式）**：
  - **当终端存在非空文本选区时**：按 `Ctrl+C` 复制选中文本到剪贴板并清除选区，**不向串口发送 `0x03`**；
  - **当终端无选区时**：按 `Ctrl+C` 向串口发送 `0x03`（SIGINT 中断）；
  - `Ctrl+Shift+C` 始终复制，`Ctrl+V` / `Ctrl+Shift+V` / `Shift+Insert` 始终粘贴；
  - 在“终端选项”中保留“Ctrl+C 始终发送中断”开关，兼顾不同使用习惯。
- **鼠标选择与快捷复制粘贴**：
  - 支持单击定位、拖动字符级选择、**双击按词边界选词**、**三击选整行**、**`Alt + 鼠标拖动` 矩形列块选择**；
  - 软折行（Auto-wrapped）的连续长行在复制时自动还原为单行，硬换行才插入换行符；
  - 提供可选开关“**选中即复制**”与“**右键直接粘贴**（无选区时右键粘贴，或右键菜单一键操作）”；
  - **多行粘贴保护**：粘贴内容包含换行符时，弹出紧凑预览确认框（显示行数与前几行内容，可勾选本次会话不再提示），支持 Bracketed Paste Mode（板端开启 `?2004h` 时自动包裹 `ESC [ 200 ~ ... ESC [ 201 ~`）。
- **串口窗口尺寸（Rows × Cols）边界**：
  - 物理 UART 没有带外窗口大小通知机制。为严守“不隐式向串口注入未授权命令字节”的工程边界，终端缩放时不自动发送命令，而是在终端状态栏实时显示当前网格尺寸（如 `120 × 36`），并提供一键复制/填入 `stty rows 36 cols 120` 的便捷入口。

### 3.3 T2 候选：内嵌 ADB Shell 与多标签终端工作区

- 当多会话集中操作成为明确需求并单独确认启动后，将 `SerialTerminalWorkspace` 升级为**多标签（Tabbed）终端工作区**：
  - 支持在标签栏点击 `+` 新建**串口终端标签**或**当前在线设备的内置 ADB Shell 标签**；
  - 内置 ADB Shell 通过后台受管伪终端/交互进程接入同一个 `libvterm + TerminalGridWidget` 组件，支持多开不同或相同设备的 Shell 会话；每个标签固定启动时的设备序列号，设备切换或断线独立显示状态；
  - 远程调试页仍保留“打开外部系统终端 ↗”作为回退入口；
  - **原型先行核验项**：在 Windows 上对比 ConPTY 包装 `adb -s <serial> shell` 与管道模式下的全屏程序（`vi`/`top`）及窗口大小动态同步行为，实测通过后再定型 T2 默认通道。

## 4. GPIO 调试方案

### 4.1 接口兼容与引脚身份

Agent 使用 Linux GPIO 字符设备接口，不依赖板端预装 `gpioinfo`、`gpioset`。优先探测 ABI v2；旧内核或仅启用 v1 的固件使用 v1 适配。v1 已被上游列为旧接口，因此不能把它作为长期唯一实现。内核版本、Android 版本和 CPU 架构不能代替节点、ioctl、权限与安全策略探测。接口不存在、访问拒绝和单项操作不支持分别显示；权限错误不能触发绕过限制的回退。

依据：[内核 GPIO 接口](https://docs.kernel.org/userspace-api/gpio/chardev.html)、[v1 兼容说明](https://docs.kernel.org/userspace-api/gpio/chardev_v1.html)。三目标均需核对 UAPI 结构体布局和 ioctl 编号，尤其是 ARMv7 的 64 位时间戳对齐。

- 引脚操作使用当前 Agent 实例探测到的控制器标识与行偏移；Agent 将标识映射到已枚举字符设备，不接收任意设备路径。
- `GPIO3_B4` 可计算出 bank 3、行偏移 12 和传统编号 108，但不能据此断言设备节点就是 `gpiochip3`。定位还需核对控制器名称、标签或经过验证的板级映射；映射不明确时展示候选并保留人工选择。
- 收藏按设备与控制器身份保存备注，重新连接后重新验证。节点编号变化、固件变化或映射失效时，收藏只作为定位提示，不恢复输出、不自动请求引脚。

### 4.2 能力与操作语义

以下均为拟增能力；元数据枚举使用固定只读 RPC，其余通过带参数的板级任务执行，接口扩展见第 6.2 节。

| 能力 ID | 风险 | 资源 | 参数与行为 |
| --- | --- | --- | --- |
| `gpio.chip.list` | `read_only` | 元数据短时读取 | 枚举控制器及行名称、方向、active-low、占用与 consumer；大列表分页并标明完整性。不请求行句柄、不读取电平 |
| `gpio.pin.read` | `read_only` | `gpio.line:<chip>:<offset>` | 按现有配置以 as-is 方式短时独占读取，不指定新的输入/输出方向、偏置或驱动方式。被其他进程占用则报告占用，不转为输入、不抢占；不能保持原配置时报告不支持 |
| `gpio.pin.write` | `hardware_control` | 同一行及全局工具任务位 | 明确选择物理高/低，申请输出时一并设置初值，成功后保持句柄；“释放引脚”结束持有。保持时间 1–300 秒，默认 30 秒，可通过所属任务的“延长保持”动作重设剩余时间，上限仍为 300 秒 |
| `gpio.pin.pulse` | `hardware_control` | 同一行及全局工具任务位 | 明确互为相反值的空闲电平与脉冲电平、脉宽 10–10000 ms；先建立空闲输出，再输出脉冲，正常结束回到指定空闲电平并释放。取消时尽力回到该电平后释放，失败保留实际步骤 |
| `gpio.edge.monitor` | `hardware_control` | 同一行及全局工具任务位 | 明确切换输入并监听 rising/falling/both，时长 1–300 秒，默认 10 秒；显示逻辑边沿、active-low 与时间基准，可取消。切为输入属于配置动作，不能标成纯只读 |

读取结果分别保留逻辑值与 active-low 信息；物理高/低按极性换算并注明为数字状态，不推断电压或外部负载。读取与控制均以实际句柄申请结果裁决，执行前再次核对占用。

输出与脉冲的驱动方式必须进入明确参数和确认摘要；首版默认推挽，开漏/开源仅在适配与目标已验证时开放，不自动改偏置。GPIO 输入偏置调整不纳入首版；无法按请求维持配置时返回不支持，不把内核的尽力设置当成硬件验证成功。长时间保持应显示到期提醒，“延长保持”校验原设备、实例、任务与所有者，不隐式改变电平。

as-is 读取及释放后的状态边界依据：[v1 行请求](https://docs.kernel.org/userspace-api/gpio/gpio-get-linehandle-ioctl.html)、[v2 行请求](https://docs.kernel.org/userspace-api/gpio/gpio-v2-get-line-ioctl.html)。释放表示本工具结束持有；释放后电平由硬件与驱动决定，不承诺回到原电平、低电平或高阻。

### 4.3 页面与反馈

- 页面上方为设备、能力状态和刷新；左侧为可搜索的引脚表，右侧为当前引脚详情与操作区。1366×768 下优先保留列表和操作；窄窗上下排列，详情可滚动。
- 进入页面只读取可用的元数据，不自动读电平、切输入、输出或监听。无服务时在工具页提供原因与连接入口，用户点击连接后再准备服务。
- 全量列表用于浏览；输出、脉冲和输入监听先将引脚加入带备注的常用控制列表，并在本次 Agent 实例首次配置该引脚时确认对象、动作和影响。变更极性、引脚或动作参数后重新核对；确认后仍由 Agent 校验占用与参数。
- 未占用只说明 GPIO 接口的当前状态，不能证明该引脚适合调试；控制对象需按板级连接确认。不自动改变 pinmux、解绑驱动或绕过 consumer 占用。
- 正在保持输出时显示设备、引脚、设定电平、到期时间及“释放引脚”；设定值与实际读取结果分开。超时、停止、租约失效或通信中断不显示“已恢复”，未确认释放时显示“结束状态未知”。
- 边沿事件保留内核时间戳及其时钟来源，队列上限 4096 条；通过进度游标分批传送，单批最多 256 条，终态仅保存计数、摘要与完整性，完整事件由上位机保存。事件导出最多 8 MiB，队列或导出超限均停止监听并保留不完整结果。有序号时记录缺口；旧接口无法判断内核丢失时明确标为未知。该工具用于软件观测，不承诺逻辑分析仪精度。
- 脉冲按单调时钟调度，记录请求宽度和软件实际执行间隔；调度时延、系统休眠与驱动耗时可能影响波形，硬件脉宽须实测。

## 5. 网络测速方案

### 5.1 控制通道与测试路径

```text
Windows 应用 ── ADB 回环转发 ── Agent：固定能力、任务控制、停止与状态
Windows iperf3 ── 所选电脑网卡 / 局域网 ── 板端所选网口的临时 iperf3 服务
```

PC 始终作为客户端，板端运行绑定指定地址的单次服务端。该方式减少 Windows 入站监听需求，但不承诺防火墙、终端防护或网络策略必然放行。Agent 控制端口仍只绑定回环；iperf3 的临时网口监听是显式测速动作的一部分，结束或超时后由本任务回收，不修改系统防火墙。

- 首版提供 IPv4 以太网测试。用户选择电脑网卡及源 IPv4、板端网口及目标 IPv4；客户端绑定所选源地址，启动前核对两端到对端的路由与地址仍有效，报告保留两端地址及实际可确认的出口。源地址绑定不能单独证明使用了预期物理接口；已知路径发生变化时停止并标明原因。
- 回环、ADB 转发地址不能作为测试目标。虚拟网卡、VPN、Wi-Fi 与 USB 网络须明确识别，首版不将它们自动当成物理以太网；无法确认路径时不能给出“以太网验收通过”。仅检查目标不是 `127.0.0.1` 不足以证明路径正确。
- 板端 `network.interface.list` 返回接口身份、IPv4、链路状态、MAC、速率/双工及累计计数，未知字段保留空值。默认按需读取；测试中最多每秒一次，并记录读取开销。
- 链路协商速率与实际吞吐分别显示。未配置目标速率时只展示观察值，不凭网口名称或百兆协商值推断不合格。

### 5.2 首版参数与能力

| 项目 | 范围与默认值 |
| --- | --- |
| 方向 | “电脑发送 → 板卡”“板卡发送 → 电脑”“依次测试两个方向”；默认依次测试，每个方向独立起停服务并保留结果 |
| 协议 | 默认 TCP；UDP 放入高级参数。首版双向为顺序执行，不开放同时双向模式 |
| 时长 | 每方向 1–60 秒，默认 10 秒；界面显示整批预计时长 |
| 并发流 | TCP 1–8，默认 1；UDP 首版固定 1，避免按流限速被误当作整批总速率。报告保留真实参数，不把多流结果与单流混为一项 |
| UDP 目标速率 | 1–1000 Mbps，默认 10 Mbps；始终显式限速，不推断该上限适合所有管理网络 |
| 端口 | 默认 5201，允许 5201–5210；占用时报告并允许重选，不停止占用它的其他服务 |
| 等待与清理 | 服务就绪最多 5 秒，连接等待最多 5 秒；每方向板端总时限为测试时长加 20 秒，停止清理最多等待 5 秒后报告确认结果 |

`network.interface.list` 是固定只读 RPC，不占长期任务位。`network.iperf3.server` 是 `network_load / runner_pack` 能力，占用本轮工具任务位及所选接口/端口；仅接受控制器提供的接口标识、当前有效绑定 IP、端口、协议和受限时限等有类型字段。Agent 从已校验 Bundle 的固定路径启动进程，不接受可执行文件路径、脚本文本、环境变量或任意附加参数。

iperf3 的 `-b` 对各并发流分别限速，UDP 单流规则由 UI 与参数校验同时执行；服务端设置所选版本支持的最大时长与速率限制，Agent 自身仍保留独立硬超时。依据：[iperf3 参数说明](https://software.es.net/iperf/invoking.html)。

### 5.3 启停与结果归属

1. 固定设备、Agent 实例、两端接口和本批参数，检查能力、工具摘要与同设备活动任务。
2. Agent 绑定指定板端地址启动单次 iperf3 服务，检查所属子进程仍存活并确认其监听 socket。只检查端口被占用不能证明本任务就绪；也不能通过预先建立 TCP 连接探测就绪，以免消耗单次会话。
3. 收到对应任务的就绪状态后，再启动本地客户端并绑定所选源地址。首版在实际传输前展示路径和参数，点击“开始测试”才发流量。
4. 独立读取 stdout/stderr，处理分片、进程提前退出、拒绝连接、接口消失、地址变化与解析失败；失败不自动重跑整批测试。
5. 停止时先结束本地客户端，再请求原 Agent 取消；核对本任务子进程退出及其监听消失。以进程身份而非进程名/端口号清理，不影响其他 iperf3。
6. 顺序双向仅在前一方向正常收尾后启动下一方向。用户停止、断线或失败后保留已完成方向，剩余方向标记未执行。
7. 若其他客户端抢先使用单次服务、测试对端与请求不符或输出身份无法关联，则报告结果不匹配，不接收为本次测速结果。

### 5.4 实时数据与报告

- 优先使用已验证产物支持的 `--json-stream`。普通 `-J` 默认在结束时输出，`--forceflush` 只处理缓冲，不会将它变为逐秒 JSON；仅支持 `-J` 的版本只提供结束报告，不显示伪造的实时曲线。依据：[iperf3 输出说明](https://software.es.net/iperf/invoking.html)。
- iperf3 输出包含小数，不能直接交给当前仅接受整数的 Agent JSON 模型。输出适配器使用支持标准数值的有界解析；控制协议继续采用整数基础单位：速率 bps、抖动微秒、丢包率 ppm 均四舍五入到最接近整数，0.5 向上取整。丢包率由丢包数/总包数计算，总包数为 0 时标为未知；非有限数、越界值或无效字段不转成 0。保留独立原始 JSON，不为此放宽所有控制消息的数字规则。
- 每条流式记录最多 256 KiB，单方向累计 stdout/stderr 各最多 8 MiB；超限停止并标记结果不完整。曲线按秒保留有界样本，最终摘要以完整终态数据为准。
- 页面展示进度、两个方向各自的发送/接收速率、TCP 重传或 UDP 抖动/丢包；CPU 占用只显示来源实际提供的值及测量端。链路速率、CPU 限制和路径状态作为背景信息，不自动归因为网卡故障。
- 报告包含设备/Agent 实例与任务 ID、时间及时区、桌面/Agent/两端 iperf3 版本、接口和 IP、全部测试参数、每方向状态、完整性、指标、原始输出和清理结果。GPIO 使用相同报告封装并保存自身操作步骤与事件，报告导出不接触板端文件。

### 5.5 工具来源与离线分发

上游未正式支持 Windows，不能把任意社区二进制直接认定为可发布产物。先选定可复现或可追溯的 Windows x64 构建，验证所需 TCP/UDP、反向、绑定、流式输出和进程清理；若有缺项，记录限制并调整首版能力，不静默换成另一种测速协议。依据：[iperf3 官方 FAQ](https://software.es.net/iperf/faq.html)。

- 固定 Windows、Android ARMv7/ARM64、Linux aarch64 的源码版本、补丁、工具链和摘要；优先统一版本，不能统一时验证客户端/服务端组合与输出 schema。
- Windows 产物、运行时和许可证放入受控依赖目录；不仅核对 iperf3 本体，也核对配套运行时的许可与来源。实施时更新 [第三方依赖](../THIRD_PARTY.md)，运行时不联网下载。
- 板端 iperf3 作为 `role=runner` 纳入生成的 `build/agent-bundle/manifest.json`；该清单由构建脚本产生，不在不存在的 `src/agent/bundle/` 中手工维护。矩阵、清单生成、桌面复制、部署、执行权限、依赖和 SHA-256 校验均需覆盖 Runner，不能仅确认清单能列多文件。
- 隔离目录用于构建和离线验证。本地最终发布 ZIP 按用户安排延后；工具源码/产物来源登记与 Bundle 集成仍是功能交付的一部分。

## 6. 工具箱与共用任务规则

### 6.1 导航与设备上下文

```text
主导航
├── 串口调试
│   ├── 单串口调试
│   ├── 双端调试
│   └── 串口终端
├── ADB 调试
│   ├── 远程调试
│   └── 文件传输
├── 工具箱
│   ├── GPIO 调试
│   └── 网络测速
└── 设备信息
```

- 沿用现有父级恢复上次子页、独立箭头展开和二级选中规则；首次进入工具箱打开 GPIO 调试。各工具独立页面，参数、状态和结果各自保存，不增加嵌套模式页签。
- 共用顶部当前设备与服务状态。GPIO 及自动管理板端的测速要求对应服务能力；打开工具页不自动部署、提权或开始测试。不可用时显示原因，映射未确认的功能不提供可点击占位入口。
- 任务固定启动时的设备、Agent 实例和参数。切页保留任务，活动栏显示原设备和停止动作；切换顶部设备不迁移任务，当前页面不将原设备结果当成新设备结果。首版全局只允许一个工具任务（含短时电平读取，元数据枚举除外），其他设备也不会暗中启动第二项。
- 编辑草稿与运行参数快照分开；正在操作的参数锁定，刷新或旧回调不覆盖草稿。设备变化、失败、取消、超时和未确认结束分别呈现。

### 6.2 参数、进度与任务所有者

方案制定时的 `BoardTestRunRequest` 只含能力 ID/版本，`job.start` 严格拒绝其他参数；运行中的 `result` 为 `null`。以下记录扩展设计，实施后的确切字段与兼容语义以协议契约为准。

- 对新能力扩展 `job.start` 的有类型 `arguments`，由每项能力白名单校验名称、类型、范围、组合和序列化上限；旧无参能力仍按原请求处理，未知字段继续拒绝。`gpio.chip.list`、`network.interface.list` 采用固定只读 RPC，仅访问枚举元数据，不占长任务位。
- 执行类请求携带操作标识，有界保存去重记录；同标识同参数关联原任务，同标识不同参数拒绝。启动回复丢失时先按操作标识查询归属，不自动重发输出、脉冲或测试；去重记录已过期而无法确认时拒绝重放，先完成状态复核再接受新的明确操作。
- 新增固定 `job.progress` 查询运行阶段、就绪状态、有界事件游标及完整性；保留原 `job.status` 的状态与终态结果语义，不将半成品塞入其 `result`。进度是只读快照，单批最多 256 条事件，GUI 通知合并，轮询间隔不短于 100 ms；游标落后时报告缺口，不能无限缓存或按日志文字猜测状态。
- 新工具任务附带随机所有者标识，并与 Agent 启动实例、任务 ID 共同核对；进度、续租、延长保持与取消均校验这组身份。固定 `job.renew` 负责刷新租约，`job.progress` 不续租；仅供输出保持使用的固定 `gpio.hold.extend` 负责显式重设剩余保持时间。普通健康探测、旧连接和其他调用方不能延长或取消任务；Agent 重启后旧 ID 不得作用于新任务。所有者标识用于归属，不代替认证。
- 对新任务建立 5 秒租约，上位机独立后台调度每秒续租一次，切页不停止续租，续租不依赖 GUI 事件循环。租约过期后 Agent 取消任务，目标在 1 秒内结束本工具的句柄/子进程持有；该时限需单独验证。GPIO 保持期限、监听时长和网络总时限独立于租约，`job.renew` 不能延长这些期限；到期只取消与释放，不自动重启。
- 截止时间判定先于续租或延长保持，迟到请求不能使已过期任务复活；取消已被接受后也不再接受续租或延长。
- 板端租约与任务截止时间使用能计入休眠时间的时钟。板卡自身休眠时用户态不能执行清理，恢复后先处理过期任务并记录实际延迟，不承诺休眠期间电平已释放；应用恢复也先复核原任务，不能先续租旧操作。
- 用户断开服务、停止任务或退出时立即请求取消；控制连接失联、应用崩溃或主机休眠时依靠租约与硬时限收尾，不能依赖 socket 立即报错。未取得终态时上位机保留“结束状态未知”，重连后先查询原实例，不自动恢复输出或重跑测试。
- 计划沿用协议 1 的帧与现有方法语义，新增接口以工具能力及版本协商；实现前把确切请求/响应、实例身份获取和错误码落入唯一 [协议契约](../AGENT_PROTOCOL_V1.md)。必须用旧无参请求、严格响应解码与新旧 Agent 组合证明兼容，不能仅因版本号未变就认定兼容。

### 6.3 首版资源与互斥

| 场景 | 拟实施规则 |
| --- | --- |
| GPIO 列表 / 网络接口枚举 | 短时只读、限频，可与当前工具任务共存；不请求引脚、不创建测速连接 |
| GPIO 读取 | 占用现有板级任务位和行资源；遇到其他任务/外部行占用时明确提示，不排队后突然执行 |
| GPIO 输出保持、脉冲、监听 / 网络测速 | 全局一次一个工具任务，板端继续单板级任务约束；保持输出也算活动任务。先停止/释放并确认，再开始另一项 |
| 设备信息读取 | 与工具共用当前板级任务约束；工具活动期间延后或提示占用，已显示只读结果可保留并标明时间 |
| 同设备 Root、Remount、重启、部署或服务重置 | 工具结束并确认收尾后执行，结束未知时仍阻止；其他设备和本地 COM 按原规则独立工作 |

资源声明与执行前检查均由 Agent 裁决，UI 提示提前反馈。同设备多引脚保持、GPIO 与测速并行是后续需求，不在本轮建立通用并发资源调度器；已有录制、普通发送和可靠性压测的状态机保持各自职责。

## 7. 分层与工程边界

- GPIO 观察值、参数、任务与 iperf3 协调逻辑放在无 Qt 的 `core/application` 和板端实现中；Qt 仅承担界面、输入与 GUI 线程桥接。阻塞操作全部在后台执行。
- 每个任务明确拥有连接、进程、引脚句柄、事件队列和导出文件；停止后异步收尾，回调核对生命周期、设备及实例。仅清理本工具拥有的资源，不按名称杀进程、不重启共享 ADB server。
- Agent 不开放任意命令或路径透传，iperf3 不提供自定义参数框；第三方固定版本、摘要与许可，离线分发。
- 当前行为继续以 `features/`、协议契约和 UI 文档为准；实际实现各批次再同步相应权威文档。候选类名和拟增方法不能写成已实现，不预建空模块，不借本轮重启旧阶段 4 的通用重构。
