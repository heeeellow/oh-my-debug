# ADR-0005：ADB 工作区、文件传输与终端候选方案

- 状态：用户确认导航后已授权开始迭代；本轮实现 ADB 工作区和手动文件传输。后续内置终端、自动目录联动及投屏后端选型仍未确定。
- 决策边界：双栏、同名普通文件显式覆盖/默认跳过、已有目录不合并，是这轮实现采用的可调整方案，不追认为用户此前已经确认的全部设计。
- 后续反馈：用户已确认应用界面继续使用 Qt Widgets，不切换 QML；新一轮 UI、交互和局部架构改进提案见第 10 节，其余建议不因此自动定案。
- 文档职责：本文维护后续方向、选型依据和待定项；当前实现、Git 交付及验证结果只由 [STATUS](../STATUS.md) 汇总，现行行为仍以对应功能契约为准。

## 1. 这轮讨论要解决什么

用户已经能正常使用串口终端，希望继续把 TestTools 做成日常板卡调试工作台。讨论从投屏集成的实际价值，逐步扩展到 ADB 终端、文件传输和配置编辑。

整体迭代包含此前讨论的 ADB 工作区、主导航与顶栏整理、现有终端和投屏入口归并，以及独立文件传输页。后续终端选型与投屏音频问题也保留在整体计划中；终端后置只调整内置终端评估的先后，不意味着把整轮迭代缩成文件传输。

文件部分已收敛到通用收发：用户自行选择设备文件或文件夹及本地保存目录，下载日志、配置等资料；需要修改时使用自己的本地编辑器，完成后再选择文件上传。未选择本地保存位置时默认桌面。文件传输使用独立页面，内置终端方案放到后面讨论。

设备目录首版手动输入或粘贴；用户可以在现有终端中 `cd`、`pwd` 后复制路径，不要求自动读取终端当前目录。用户确认文件传输和投屏控制归入 ADB 调试的左侧二级导航，随后授权开始迭代；文件区双栏布局和传输细节按首版方案实现，仍可在使用反馈后调整。


## 3. ADB 调试页面的组织方向

### 3.1 已确认的导航与终端入口

用户比较三份图像草案后，同意第三份的左侧二级导航，并同意修正父级点击行为和系统终端入口。一级导航为“串口调试 / ADB 调试 / 设备信息”，ADB 下只有“文件传输 / 投屏控制”两个页面入口。内容区不再重复放一排相同的页面页签；串口内部已有模式切换本轮不据此扩大修改。

| 操作或位置 | 已确认规则 |
| --- | --- |
| 点击 ADB 调试文字 | 直接恢复上次使用的 ADB 子页面并展开，不增加只有启动按钮的中间页 |
| 点击父级小箭头 | 只展开/收起二级导航，保留当前页面和任务 |
| 点击子页面 | 打开对应完整页面；页面切换本身不启动投屏或文件传输 |
| 系统终端 | “打开系统终端”放在 ADB 内容区工具栏，作为外部窗口启动动作，不占左侧子页面 |

本轮首次进入 ADB 默认文件传输，只突出当前子页面；父级恢复本次运行中最后子页，不跨启动记忆。顶栏只保留设备上下文，ADB 在线与设备信息内的 Agent 就绪分开表达。


### 3.2 本轮页面组织与保留边界

- 文件传输使用 ADB 下的独立完整页面，本轮采用本地/设备双栏、Ctrl/Shift 多选和逐项传输记录，具体规则见 [文件传输契约](../features/FILE_TRANSFER.md)。
- 投屏控制区内嵌，画面保留独立窗口；现有截图和常用控制沿用，未增加画质选项或内嵌视频。
- 1366×768 下按需展开或切换，不强制终端、投屏、文件三块始终并排；延续现有克制的 Qt 界面风格。
- 辅助操作靠近对应对象；文件权限放在文件区域，投屏操作放在画面区域。
- 页面切换本身不结束会话。活动会话和传输固定绑定启动设备，顶部改选设备不能让运行中的控制或文件传输悄悄指向另一台设备。
- 无设备时仍可进入页面查看连接提示；Linux ADB 可使用终端和文件功能，安卓投屏单独判断支持条件。
- 具体功能是否可用放回对应区域；原顶栏“功能·未就绪”状态移入设备信息。

## 4. 终端方案：参考 Tabby，优先复用成熟核心

用户本轮明确终端方案后续再讨论。本节保留候选资料，不作为独立文件传输页的实施前置条件。

### 4.1 参考价值与现有边界

讨论时核对的 Tabby 源码中，应用使用 Electron、Angular，终端模块依赖 xterm.js。可以参考其终端核心复用、输入交互、会话与显示分离，以及终端附近的文件操作；没有决定将整个 Tabby 打包或迁移其应用架构。

TestTools 目前是 Windows x64、C++17、Qt Widgets。现有 ADB 终端的行为见 [ADB 终端契约](../features/ADB_TERMINAL.md)；现有串口终端的兼容范围见 [串口终端契约](../features/SERIAL_TERMINAL.md)。后者是有界、面向行的控制台，不具备完整备用屏幕、滚动区域和字符宽度表，不能接上 ADB 就宣称兼容完整 TUI。

### 4.2 两条候选接入路线

| 路线 | 收益 | 需要承担的工作 |
| --- | --- | --- |
| xterm.js + 嵌入式 WebView | 复用较完整的终端交互、全屏程序支持、中文与输入法处理；主应用仍可保留 Qt | 评估 WebView2 或 Qt WebEngine、原生桥接、打包与运行时依赖、实际资源占用 |
| 原生 Qt 显示 + libvterm 等终端核心 | 终端解析与 Qt 解耦，避免为终端单独引入完整 Web 渲染运行时 | Windows/MSVC 构建适配、绘制、选择复制、回看、输入法、字符宽度和性能仍需开发 |

xterm.js 是终端前端，不提供 ADB 会话、文件权限或当前目录联动；libvterm 也不是完整 Qt 控件。QTermWidget 官方列出的兼容平台为 BSD、Linux、OS X，不能因为名称带 Qt 就假定 Windows 可直接接入。

若采用内置方案，目标应覆盖普通 Shell、实时输入、Tab 补全、历史、中断、复制粘贴、中文、窗口大小变化，以及设备具有相应程序时的 `vi/top` 等全屏使用。是否同时升级串口终端另行确定，不在选型阶段擅自替换已经可用的串口路径。

后续重新讨论内置终端时，适合做小型接入验证，比较上述两条路线的真实交互、依赖体积和维护成本，再形成正式决策。尚未安装这些依赖、编译候选终端或测量内存，不能承诺具体完成天数、轻量程度或完整兼容性。

## 5. 独立文件传输页

### 5.1 目标流程

1. 用户选择目标设备，在独立文件传输页输入或粘贴设备目录，浏览、筛选并选择文件或文件夹。
2. 选择本地保存目录后下载；未选择时使用桌面。拉取日志等普通下载不要求后续编辑或上传。
3. 上传时由用户选择本地文件或文件夹，并明确设备目标目录，再执行上传。
4. 如需修改配置，用户自行在本地编辑，完成后重新选择文件上传；工具不维护编辑会话、待写回状态或保存后自动上传。
5. 展示传输进度和成功、失败、取消结果；批量传输不能用部分成功代替整体结果。

普通上传下载复用项目统一解析的 ADB，通过 `push/pull` 完成，不依赖投屏是否开启，也不需要新增任意 shell Agent RPC。项目现有 Agent 部署中的 `push` 调用可作为基础参考，用户文件传输仍需自己的后台进度、取消和生命周期。

本轮以左右双栏实现上述流程，文件夹保留名称和层级，普通文件默认跳过、允许明确覆盖，已有目录首版不合并。
具体暂存、权限、取消和结果要求统一见 [文件传输契约](../features/FILE_TRANSFER.md)。拖放、常用路径记忆及目录合并继续保留为后续选项；文件传输不自动安装 APK，也不因文件类型触发配置重载或其他设备动作。

### 5.2 首版手动目录与后续联动

现有外部 Windows Terminal/cmd 内的 `cd` 只影响那个远程 Shell。另起 `adb shell pwd` 得到的是新会话目录，不是用户正在使用的会话目录；内置显示控件本身也不会解决这个问题。

首版文件页独立维护浏览路径，用户直接输入绝对路径，或在原 Shell 执行 `pwd` 后复制粘贴。后续如确有需要，再评估辅助命令、Shell 集成或目录上报；讨论中举例的 `ttfiles .` 目前不存在。不能根据输入文本猜测 `cd` 结果，也不把自动目录联动作为文件传输的验收前提。

### 5.3 权限与文件完整性

- 分别判断读权限、写入/替换所需权限、目录访问权限和挂载状态；`/system`、`/vendor` 不能仅根据 `rwx` 判断可写。
- 终端执行 `su` 不会让独立的 `adb push/pull` 继承 root。普通 adbd、root adbd、设备支持的显式提权中转需要区分；中转方式是否支持及其参数另行定义。
- `adb root` 会重启 adbd，可能影响终端、投屏与传输；root、remount/OverlayFS、可能涉及重启的分区准备应作为明确操作。不能通过笼统的 `chmod 777` 或关闭 SELinux 处理所有失败。
- Android root 仍可能受 SELinux 限制；只读文件系统、固件构建类型、验证启动和具体策略都影响上传能力。展示原因与可执行下一步，不自动承诺绕过限制。
- 上传覆盖时需明确属主、权限、SELinux 标签和软链接的处理方式；传输不自动转码或改换行，保持用户所选文件的实际字节。
- 同名覆盖、部分传输、取消和断线的处理由功能契约明确，不能静默覆盖或把不完整文件显示为成功。本轮采用同文件系统暂存后替换，不增加长期备份管理；属性与权限失败必须保留为失败结果。
- 失败不删除用户已有的本地文件，未完成下载与完整文件需要区分。任务固定绑定设备和路径，重连不能把旧任务迁移到另一设备；上传成功与配置已被服务重新加载是不同结果。

上述是通用文件传输的权限和完整性边界。此前讨论的本地工作副本管理、外部编辑器监听、编辑冲突检测和自动写回不进入当前方向；实际板卡工具、权限和 SELinux 支持范围仍需结合用户目录验证。

## 6. 投屏与音频调试的取舍

用户的历史经验是：scrcpy 投屏时出现板端无法正常播放声音，而同场景使用 ARDC 正常；同时用户更认可 scrcpy 的轻量体验。这是用户证据，尚未完成相同版本、设备与音频路径下的对照定位，不能直接归因为硬件声卡被独占。

讨论中核对的 scrcpy 4.1 官方行为：默认开启音频转发，默认 `output` 使用 Android `REMOTE_SUBMIX` 并关闭设备本地播放；`--no-audio` 关闭音频功能，不等于电脑静音。Android 13+ 的 `--audio-dup` 可在捕获时保留设备播放，但应用可以拒绝捕获，也不能据此认定 AEC、录音和参考通道不受影响。

当前集成的默认音频策略及投屏行为见 [投屏契约](../features/SCREEN_MIRROR.md)，共存验证状态见 [STATUS](../STATUS.md)。需要对照纯画面投屏前后的播放、录音、AEC 等实际音频链路，取得实机证据后才能判断是否满足调试要求。

当时评估继续评估 scrcpy 的纯画面与输入模式，音频诊断/监听单独设计、明确开启；ARDC 保留为已知可用的外部备选，没有确认其公开集成接口或二次分发条件。不能宣称已经证明 ARDC 集成更优，也不在本轮替换后端。

完整自研投屏仅在出现明确核心需求时再评估，例如脱离 ADB、面向自有固件开机待命、特定音频通道或跨网络远程维护。当前没有决定自研采集、编解码、传输和输入注入全链路。复用成熟投屏/终端核心与自行开发调试工作流可以同时成立。

## 10. 新一轮实现提案：Qt Widgets 交互与界面完善

### 10.1 已确认方向与提案边界

用户反馈文件页与草案有明显差距，缺少文件图标、成熟文件管理器的操作体验；串口页没有同步统一，投屏辅助按键占据主要面积。
上次检查还发现 `/sdcard` 是可访问的目录链接，却因 UI 只允许进入普通目录而被阻止。链接浏览与真实权限失败需要分开处理。

已确认应用主体继续使用 Qt Widgets，不切换 QML。用户主要通过投屏操作测试工具、客户 APK、系统设置、Wi-Fi/4G/蓝牙和浏览器；
安装沿用其拖放习惯，不需要另建 APK 管理页面。现有左侧二级导航继续沿用。

具体落地行为以功能契约为准，当前实现与验证只在 STATUS 汇总。内嵌投屏、目录合并、录屏和额外快捷入口仍按下文分别处理。

### 10.2 推荐主范围

| 工作包 | 具体交付 |
| --- | --- |
| 文件浏览缺陷 | 分别识别普通目录、文件、目录链接、文件链接与特殊节点；允许进入可访问的目录链接；链接失效、访问拒绝和设备断线给出可区分的反馈。浏览允许进入链接不代表递归传输自动跟随链接 |
| 文件页交互 | 保留本地/设备双栏和默认桌面；补齐文件/文件夹/类型图标、详情列和排序、前进/后退/上一级、最近目录、筛选、键盘选择及复制路径；刷新保留可恢复的选择和滚动位置 |
| 文件传输操作 | 支持明确目标目录的双栏拖放及本地文件拖入；保留手动选择收发。底部任务区可收起，显示当前批次待处理、进行中及逐项结果，提供取消和失败项重试。普通文件传输不因 APK 扩展名自动安装 |
| 串口页统一 | 单串口、双端和串口终端共同采用统一的标题、工具栏、图标、字体、间距与状态反馈；接收区拥有主要空间，连接参数紧凑，发送动作靠近输入区 |
| 投屏页整理 | 围绕实际设备操作组织会话入口、电源和截图；返回/Home/多任务/音量收为紧凑辅助操作。未投屏、连接中、运行中和失败状态清楚，不通过添加大按钮填充页面 |
| 共用视觉组件 | 集中管理主题尺寸、字号、颜色、图标资源和控件状态；复用页面标题、工具栏、状态提示、空状态和错误提示，图标配合文字/工具提示与键盘焦点 |

同名普通文件继续明确覆盖/跳过；已有同名目录的合并属于独立传输语义，先保留现行规则并明确提示，不在 UI 改造时静默改变。
目录合并如进入后续范围，需先补逐文件冲突与部分成功契约。图标按统一资源与类型映射提供，避免渲染列表时反复访问设备或阻塞读取系统图标。

### 10.3 UI 层的局部重构

现有无 Qt 的串口会话、终端解析、文件传输和投屏服务继续承担用例与资源生命周期。Qt 模型、控件、委托和界面协调均放在 `src/ui/`。

- 主窗口负责导航、全局设备上下文与页面装配，逐步减少控件细节和页面状态协调。
- 两端文件区复用文件窗格；列表模型提供行数据与稳定身份，排序/过滤由代理模型承担，图标与行展示由委托处理。目录加载、选择、位置保留及错误状态由页面协调，实际 I/O 仍交给应用服务和适配器。
- 串口按连接栏、接收监视器、发送区、快捷指令和终端视图拆分可复用组件；页面协调模式与服务状态。拆分按职责进行，不按行数机械切文件，不复制发送、计划发送或压测状态机。
- 静态布局可选用 Qt Designer 的 `.ui`，重复和动态结构保留在小型 C++ 控件中；不要求把所有旧界面一次性转换。
- 不引入通用插件框架或全量架构重写；每次提取组件都对应本轮实际使用和独立验证需求。

技术依据：[Qt 模型/视图与委托](https://doc.qt.io/qt-6/model-view-programming.html)、[Designer UI 文件](https://doc.qt.io/qt-6/designer-using-a-ui-file.html)。
这些是工程设计依据，不表示更换模型本身已经证明界面流畅。

### 10.4 投屏画面内嵌单独验证

“页面内操作，同时可以弹出独立窗口”保留为优先验证的候选，不视为用户已确定的交付形式。
画面宿主与投屏会话分离，先验证 scrcpy 窗口接入、鼠标/键盘与中文输入、焦点、缩放/DPI、拖入 APK 安装、弹出/回嵌、切页和退出收敛。
Qt 的外部窗口支持与平台有关，不能只凭接口或渲染图承诺效果，见 [QWindow 外部窗口接口](https://doc.qt.io/qt-6/qwindow.html#fromWinId)。

验证通过后再决定默认画面形式；未通过则保留独立窗口，文件和串口的交互完善可以独立交付。
设置页快捷入口保留候选；APK 管理、录屏、画质档位、额外诊断面板、内置终端及自动目录联动后置。
音频共存依旧需要独立实机证据，不能由界面或纯画面参数推定通过。

### 10.5 实施与验收顺序

1. 保存当前未提交工作与迭代级差异范围，细化文件链接和界面状态契约；建立共用尺寸、字体和图标规范。
2. 制作实际 Qt Widgets 的文件、串口和投屏页面样板，检查正常、空白、加载、禁用和失败状态；图像草案只作参考，真实控件作为交互验收对象。
3. 按文件列表与窗格、串口组件、投屏控制区逐步接回现有服务；每个阶段保持可以构建和运行。内嵌画面的接入试验独立进行。
4. 集中完成行为、性能、界面与实机验收，再同步现行功能契约、UI 文档和 STATUS；提案中未实施内容继续保留候选标记。

必要验证：

- 文件：`/sdcard` 目录链接、失效链接、权限拒绝、中文/特殊字符、拖放目标、同名冲突、取消/断线/失败重试、设备切换和关闭；核心检查不跟随意外链接、不误写其他路径。
- 串口：普通/HEX 发送、共享行尾、快捷指令、搜索、计划发送、双端验证和终端键码/粘贴回归；UI 拆分不改变发送字节和任务归属。真实串口可用时另记实机范围。
- 性能：以约 1000/10000 项样本检查加载、筛选、排序、滚动和刷新位置保留，记录界面响应与目录 I/O 耗时；不承诺由截图证明流畅。
- 界面：三页在 1366×768、1920×1080 和 100%/125%/150% DPI 下核对图标、文字、焦点、点击区域、错误恢复和任务状态。
- 工程：Release/Debug、核心与目标 UI 检查、依赖边界、文档链接与迭代差异范围；构建、假后端、实机和未验证项分别记录。

## 11. 本轮补充：串口导航与图标

用户在实施期间指出串口仍使用顶部模式栏，与 ADB 的左侧导航不一致。本轮将串口的单串口调试、双端调试、串口终端
也放入左侧二级展开，父级恢复当前子页，箭头仅展开/收起；活动串口与任务的切换保护不因导航调整而放宽。
页面内不重复显示模式页签，具体导航规则见 PRODUCT 和串口契约。

按钮图标采用减法：文字可说明的动作以文字为主，目录导航、刷新和保存等沿用熟悉的标准符号；文件类型保留必要图标。
不引入生成式装饰图标，也不为“统一”给所有按钮补图标。Qt Widgets 与局部组件拆分的方向继续有效。

## 12. 0.8.0 确认范围：文件图标、自动刷新与连接反馈
